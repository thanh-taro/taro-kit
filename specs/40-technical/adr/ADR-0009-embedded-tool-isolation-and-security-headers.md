## Context
NFR-08, F-003.R3 and RULE-10 require that an embedded tool:
- runs isolated, with only its declared permissions;
- never reads or changes the portal's content or personal data;
- never navigates the portal page;
- cannot navigate its area to an address outside its own site;
- is loaded only from catalog sites.

At the same time, an own tool must keep its own storage whether it is embedded or opened directly (F-003.R8, ADR-0001). It must therefore keep its real origin inside the frame, so an opaque-origin sandbox is not an option.

The portal must also make no third-party requests (NFR-05). Browser enforcement differs by engine: Permissions Policy delegation is complete in Chromium and partial in Gecko and WebKit.

## Decision
- **Frame:** each embedded tool is an `<iframe src="<tool url>" title="<name> tool">`, built by MOD-ToolHost (the `src` also carries `?theme=`, ADR-0011).
  - The base sandbox is `sandbox="allow-scripts allow-same-origin allow-forms"`.
  - The frame **never** gets `allow-top-navigation`, `allow-top-navigation-by-user-activation`, `allow-modals` or `allow-storage-access-by-user-activation`.
  - `credentialless` is never set, because it would partition the tool's storage.
  - The frame has `referrerpolicy="strict-origin"`.
- **Permission mapping (RULE-10 to the platform):**

| Permission | Granted by |
|---|---|
| clipboard-read | `allow="clipboard-read"` |
| clipboard-write | `allow="clipboard-write"` |
| downloads | sandbox token `allow-downloads` |
| file-pick | no platform switch exists. File inputs work in any frame that runs scripts. Declarative only; SP-3 confirms. |
| popups | sandbox tokens `allow-popups allow-popups-to-escape-sandbox` |
| fullscreen | `allow="fullscreen"` |
| camera | `allow="camera"` |
| microphone | `allow="microphone"` |

- **Content-Security-Policy (meta, emitted per page by Astro `security.csp`):**
  - `default-src 'self'`, with `script-src` and `style-src` as `'self'` plus per-page hashes;
  - `img-src 'self' data:`, `font-src 'self'`, `connect-src 'self'`, `worker-src 'self'`, `manifest-src 'self'`;
  - `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`;
  - **`frame-src` set per page, to the one origin of that page's embedded tool**, injected only on `/t/<id>/` pages at build. All other pages send `frame-src 'none'`. Linked and hidden tools get no frame-src. Spike SP-5 measured a site-wide list at 398 origins and 16.4 KB of CSP on every page with 500 tools.

  Because frame-src is checked on every navigation of the frame, navigating to any other origin is blocked and the portal page stays put (F-003.AC5).
- **Response headers (`_headers`, generated by MOD-SecurityPolicy):**
  - `Content-Security-Policy: frame-ancestors 'none'; object-src 'none'; base-uri 'self'`. This second policy only adds what a meta tag can't express.
  - `Permissions-Policy`, listing per feature exactly the tool origins that declare it, for example `camera=("https://scan.example")`, and `()` for undeclared features. This lets a granted frame actually receive the feature.
  - `Referrer-Policy: strict-origin-when-cross-origin`, `X-Content-Type-Options: nosniff` and `Cross-Origin-Opener-Policy: same-origin`. COEP is not set, so tools need no CORP headers.
- **Build guard (proposed, see "Consequences"):** an embedded tool whose origin equals the portal's origin is a build error. Combining `allow-scripts` with `allow-same-origin` on a same-origin frame would let the frame remove its own sandbox.

## Alternatives considered
- **Opaque-origin sandbox (no `allow-same-origin`).** It is the strongest isolation, but the tool loses its storage and service worker. That breaks F-003.R8 and offline-capable tools.
- **The iframe `csp` attribute (CSP embedded enforcement).** Chromium only, and it needs each tool to opt in. Not portable (NFR-10).
- **Fenced frames or portals.** Not available across engines, and they are aimed at ads.
- **Proxying tools through the portal origin.** Breaks the separate-project principle (PRN-01). It would also put tools on the portal's origin, which is the exact escape this ADR prevents.

## Consequences
- **Engine gaps (SP-3).** Gecko and WebKit do not gate clipboard writes through Permissions Policy. A tool without `clipboard-write` may still write after a user gesture there, so F-003.AC3 may pass only on Chromium. `file-pick` can't be withheld on any engine. These limits likely need a spec note in RULE-10 saying that permissions are granted "where the browser can restrict them". That change is for the user to approve.
- **Frame navigation between tools.** A frame can still navigate to another catalog tool's origin. That target is on the same site (ADR-0001), so RULE-10 still holds.
- **The `allow-forms` base token** is a technical reading of "can run its own code". It needs confirmation as a RULE-10 clarification.
- **The build guard** for an embedded tool on the portal's own origin is a new validation. It should be added to INV-03 or RULE-10 by a spec change.
- **Hashes and CSP derivation run at build**, so adding a tool regenerates both automatically (F-001.R1).

## Amendments from spike SP-4 (2026-10-13)
- Per-page CSP: the layout inserts `frame-src` with only that page's tool origin, and `'none'` elsewhere. `worker-src 'self'` and `manifest-src 'self'` are set. Service-worker-served pages keep both the meta and the header policy, with zero violations measured (U-4 closed).
- When the connection returns, the tool view reloads a paused (offline-state) frame itself, so F-003.R6 needs no manual reload.
- WebKit: a tool's own service worker registered on a direct visit does **not** control the same tool while embedded, although localStorage is shared. An embedded offline-capable tool works offline only after it has been opened inside the portal while online.

## Amendments from spike SP-3 (2026-10-13, live on lab.tarokit.app)
- **Permissions-Policy allowlists must include `self`**: `feature=(self "https://tool.tarokit.app")`. With only the tool origin (`feature=("origin")`), Chromium denied every delegated feature, even in granted frames. With `self`, each granted capability works and every other is refused; the baseline frame refuses clipboard-write.
- Per engine: Chromium enforces clipboard-read/write, fullscreen, camera and microphone delegation. WebKit cannot withhold clipboard-write. No engine can withhold file input (`file-pick` is documentation only). Downloads and popups follow the sandbox tokens.
- **Popups**: they open, but `window.open` returns null because of the portal's COOP (`same-origin`). Tools must not depend on the opener reference.
- **`allow-forms` stays in the base sandbox**: without it Chromium never fires `submit` at all.
- **Cloudflare zone**: the zone injects the Web Analytics beacon into HTML unless Web Analytics automatic setup is off. Pages also send `Cache-Control: no-transform` as a second guard (NFR-05).
